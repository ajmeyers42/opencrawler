# Customer-facing response summaries

Sanitized paste-ready answers for a migration Q&A table. Replace the repo base URL when sharing externally.

| # | Category | Priority | Response (summary) | More detail |
|---|----------|----------|-------------------|-------------|
| 1 | Index Templates | HIGH | Keeping only `.` `/` `-` via `pattern_replace` is usually too aggressive for free-text search. Prefer a custom analyzer that strips or maps **specific** problem characters (or a `mapping` char_filter), and keep alphanumeric tokens. Use a separate `keyword` / `keyword`-normalized multi-field for exact IDs/SKUs/paths. Validate with the Analyze API before changing production. | [01-special-characters.md](./01-special-characters.md) |
| 2 | Index Templates | HIGH | Nick is right: App Search auto-created `.delimiter`, `.enum`, `.joined`, `.prefix`, and `.stem` subfields are an App Search schema convention, not something you must recreate 1:1 on Elasticsearch. Replace the *behaviors* with native analyzers and multi-fields: `keyword` for exact/enum, stemming analyzer (or `quote_field_suffix`) for stem, `search_as_you_type` / edge n-grams for prefix, and word/path tokenizers for delimiter-style matching. That reduces index bloat and matches how Search Applications / ES queries work on 9.x. | [02-app-search-derived-fields.md](./02-app-search-derived-fields.md) |
| 3 | ILM | MEDIUM | “Policy enabled” does not guarantee tier moves. Confirm: (1) the index/data stream actually uses that policy, (2) `min_age` / rollover conditions have been met, (3) the deployment has nodes with the **cold/frozen/warm** roles the policy names, and (4) explain API / ILM explain shows the current phase and any allocation errors. Cloud logging streams often stay hot unless cold/frozen capacity exists. Happy to walk the policy + node roles on a short call. | [03-ilm-tiers.md](./03-ilm-tiers.md) |
| 4 | Crawler | MEDIUM | Elastic’s crawler / Open Crawler index templates often set `dynamic: false` (or strict schemas) so crawled fields stay predictable for search apps and pipelines. Dynamic mapping (and dynamic templates) remain valid when you intentionally want new HTML-extracted fields to appear without a mapping change—trade-off is mapping explosions and type conflicts. Common pattern: static core fields + selective dynamic templates for known prefixes. | [04-dynamic-vs-static-mapping.md](./04-dynamic-vs-static-mapping.md) |
| 5 | General | LOW | Behavioral Analytics was removed from the Kibana UI in 9.0; the `_application/analytics*` APIs are deprecated. On 9.4.1 there is **no BA product UI to enable**—analytics is instrumentation plus **ES\|QL queries/dashboards** (optional EDOT for search latency). Nick’s path: `page_view` / `search` / `search_click` → ingest API → events data stream → dashboards. Open Crawler does not collect this. | [FAQ-002](../../../FAQ.md#faq-002) · [behavioral-analytics-parity](../../search-analytics/behavioral-analytics-parity/) · [additional-analytics.md](../../search-analytics/behavioral-analytics-parity/additional-analytics.md) |
| 6 | General | LOW | Data Views tell classic Discover / Lens / most non-ES\|QL Kibana apps *which* indices or data streams to query (plus time field and runtime fields). Typical uses: explore crawled content, build Lens charts, set a default view per space. They are **not required** for ES\|QL-based Discover/dashboard panels. | [06-data-views.md](./06-data-views.md) |
